# 以图搜图

0.8.5 提供写真库内以图搜图，支持原图、完整截图和轻中度裁剪。它在自己的 Gravelle 服务内查找图片，结果只来自当前账号可访问且未隐藏的写真库。

## 开始使用

1. 管理员打开「设置 → 图片搜索」，启用「建立图片索引」。功能默认关闭。
2. 服务端在后台为已有作品逐页建立索引。管理页显示已索引、待处理和失败数量；关闭网页不会停止后台任务。
3. 打开「搜索」，切换到「以图搜图」。选择、拖入或粘贴一张静态 JPG／PNG／WebP 图片，点击「开始搜索」。
4. 结果按匹配程度排列，显示匹配内页、作品、写真库、模特与页码。点击结果直接阅读对应页；每次最多显示 30 个匹配页面。

首次索引未完成时，可以先搜索已收录的图片。没有结果时，先确认相关作品已完成索引，再尝试更完整、清晰的图片。粘贴图片时，将焦点放在页面空白处，不要放在文字输入框中。

## 能找到什么

支持散装图片目录与 ZIP／CBZ 作品的内页，覆盖整本作品而不只是封面。字节完全相同的文件优先显示为「相同图片」；缩放、重新压缩、保留完整画面的截图和轻中度裁剪通过指纹或局部特征及几何验证，显示为「近似图片」。使用现有上传入口即可，结果仍定位到作品与页码。

截图可包含浏览器或阅读器边框，建议让原图占据主要画面。已验证的裁剪样例保留约 45%～70% 的原图面积，同时做过缩放和 JPEG 重压缩；这是样例覆盖范围，并非任意照片的识别保证。微小裁片、低纹理、严重模糊、重复图案、大面积遮挡或拼图可能无法确认；镜像和重度水印不作保证。

近似匹配不代表人物识别或语义理解。当前不提供全网找图、按人物身份找其他照片或服装／场景搜索。没有结果不表示写真库中一定不存在原图；近似结果也需要自己确认，不显示未经验证的准确率百分比。

## 索引管理

| 操作 | 结果 |
| --- | --- |
| 暂停／继续 | 暂停或恢复后台建索引；暂停期间仍可搜索已收录且仍有效的图片。 |
| 重试失败图片 | 将失败页面重新加入处理队列，不必重建全部索引。 |
| 重建索引 | 立即清除现有图片搜索索引，再从当前作品重新生成；旧索引不会在重建期间继续保留。 |
| 关闭「建立图片索引」 | 停止索引并关闭图片搜索，保留已有索引记录供再次启用时复核和使用。 |
| 清理索引 | 清除图片搜索索引并关闭搜索；下次启用后重新建立。 |

重建与清理需要确认。以上操作不删除源图片、优化图片、作品资料、书签或阅读记录。

点击「失败 N 张」可以展开失败列表，每页按需读取 20 条，显示作品、图片名、失败原因及对应阅读页入口。可单张或批量重试可恢复的失败项，已有成功索引保留。明确不支持的实际格式会显示具体格式并禁用重试；修复或替换源文件后先扫描写真库，再处理新的索引任务。失败列表不会扩大格式支持范围。

写真库扫描后增量更新新增或变化页面，移除、排除的作品不再作为搜索结果。搜索和预览会复核源文件版本，变化后的旧索引不会继续返回旧图片；移动或替换源文件后，应重新扫描写真库。索引任务及暂停状态保存在服务端，服务重启后按当前设置恢复。

旧索引首次升级会自动逐页补充截图／裁剪所需的局部特征，无需手动重建。补充期间已收录页面仍可做原有整图搜索和预览；局部特征完成后该页才支持裁剪匹配。补充失败保留原有指纹，可通过「重试失败图片」恢复。

只有管理员可以开关、暂停、重建、重试或清理全局索引。子账号只能搜索管理员授权范围内的作品，不能查看全局索引数量。个人隐藏的写真库、已移除作品和因图片优化尚未公开的作品均不出现在结果中；结果预览与阅读入口同样检查权限。

## 数据与性能

搜索图片只上传到自己的 Gravelle 服务，经内存和受限子进程处理，不作为临时文件保存，不导入写真库，也不建立搜索图片历史。页面指纹、局部特征和最长边 384px 的 JPEG 预览保存在服务端 `library.sqlite3` 的 `is_pages` 表中，各账号共用；源文件不被修改。局部特征最多 512 点，连同候选签名每页最多增加 22,538 字节（约 22 KiB，未计 SQLite 页及记录开销）。索引过程的临时副本位于资料目录 `image-search-work`，任务结束后清理。Docker 中这些资料随 `/data` 保存，不使用图片优化目录 `/data/transcoded`。

索引与查询共用一个图片解码进程槽位，并与图片优化共用服务端的任务名额。「设置 → 性能设置」中的后台任务并发数默认 1，后台按单张图片排队；管理员可设置 1～8，提高后可让优化与索引同时运行，或让不同作品同时优化，索引自身仍保持单路。实际搜索解码遵守共用名额，等待时优先于新的后台任务，不中断正在处理的图片。详见 [性能设置](performance.md)。

解码与几何验证均在受限子进程内运行，每个进程内存上限 1024 MiB、超时 60 秒；候选扫描也设 60 秒预算。这些是阶段限制，不能当作整个服务的总内存上限或单次搜索总时限。局部特征基于最长边 1280px 的标准化图，候选排名流式读取紧凑签名，最多对 64 页做几何验证，避免把全库描述子装入内存。整个查询共用一个任务名额。首次索引和升级补充仍需读取、解码原图，主要消耗 CPU、内存和磁盘 I/O；无需 GPU 或下载模型，原生图像计算设为单线程。设备负担较高时可暂停索引。

索引和预览会增加数据库占用，大小取决于页数和图片内容。目前没有单独的索引容量设置；清理索引会移除相应记录，但 SQLite 数据库文件不保证立即缩小。

后台索引有限复用已导入图像库的工作进程，减少每张图片重复启动与导入的开销：最多处理 32 张或运行 300 秒，峰值内存达到 512 MiB、空闲 10 秒或发生异常时回收。每图超时、进程内存保护、源版本复核和逐图释放共享名额仍生效。前台查询继续使用独立短期进程，并回收空闲索引进程。实际提速取决于图片解码和磁盘读取占比，不能据此承诺 NAS 上的固定速度或耗时。

macOS 版的图片进程每 0.1 秒检查峰值常驻内存，超过 1024 MiB 预算即结束；这是采样保护，可能短暂超出预算。Windows／Linux 保留现有操作系统进程限制。内存监测不可用时任务明确失败，各平台仍保留像素预检与超时，详见[性能设置](performance.md)。

## 当前限制与排查

- 查询图片不超过 64 MiB、1 亿像素，只支持静态 JPG／PNG／WebP；格式按实际内容校验。索引源页面同样限于这三种静态格式，受 64 MiB 文件限制，像素安全上限为 2.5 亿；在上限内仍可能因解码内存不足、损坏或超时而失败。其他格式的页面会显示索引失败，不影响原有阅读器按自身支持范围读取。
- PNG 在打开阶段因 `eXIf` 元数据块校验异常而失败时，会在受限解码进程中尝试移除该异常块；其他数据块的结构和校验必须通过。仅处理临时解码视图，原图和原始文件摘要不变，索引与上传搜索采用相同规则。异常 EXIF 的旋转方向不被采用，有效方向信息沿用原有处理。更新后可使用「重试失败图片」重试此类页面，已有成功索引无需重建。
- 同一账号与 IP 组合每分钟最多发起 10 次搜索。另一个查询正在处理或服务繁忙时，会提示稍后重试；频率受限时请等待一分钟。
- 某一页索引失败不会阻止其他页面收录。先修复损坏、权限或资源问题，再使用「重试失败图片」；源文件有变化时先扫描写真库。
- 本地已验证 9903 × 6959 的约 6900 万像素 JPEG／PNG 解码，以及权限、隐藏、源变更和索引恢复行为。真实照片的匹配效果、超大写真库检索耗时和群晖 NAS 的资源占用仍需实测，不承诺任意图片或任意库规模都能即时匹配。
